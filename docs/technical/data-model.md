# Data model contract

The tables below are the maintained canonical schema vocabulary and retained field constraints. A registered table may be planned; registration does not prove implementation. The schema and migrations must implement these contracts. Legacy Kaneo names remain shrink-only debt in `scripts/ci/vocabulary-baseline.json`, not permission to add new legacy tables.

## Shared invariants

Identity is connection + subject; email is not a tenant key. Person organisation is immutable. Agent and customer identities remain separate. Store instants in UTC; concurrent writes use the documented version/holder predicates. Audit history and legal holds survive retention operations. Flags are runtime rows, not customer-specific source edits.

| `role` | `scope` (`instance`\|`organisation`\|`workspace`\|`project` — `organisation` exists for exactly one system role, `customer`), `workspace_id`, `key` (server-generated kebab slug, unique per `(scope, workspace_id)`, immutable), `name`, `description`, `rank`, `capabilities jsonb` (string[]), `is_system`, `is_editable`. **v**. **Delete semantics (issue #180).** `role.workspace_id` is `ON DELETE CASCADE`, but every FK that points at `role` (`membership.role_id`, `membership_grant.role_id`, `oidc_group_mapping.role_id`, `scim_group_mapping.role_id`) is deliberately `ON DELETE RESTRICT`, so deleting one role can never silently strip people's authority. Workspace deletion (the `DELETE /api/workspace/{id}` route and account erasure of a sole-member workspace) is the one path where that authority is meant to go: inside the same transaction, before the workspace row is deleted, the shared `deleteWorkspaceRoleDependents` helper explicitly deletes, in order, `scim_group_member`, `membership_grant`, `oidc_group_mapping`/`scim_group_mapping` and `membership` rows that reference a role owned by the workspace or are scoped to the workspace or one of its projects. A row qualifies by role ownership OR by scope, so a membership holding a global (built-in, no-workspace) role is removed when its scope is the deleted workspace or one of its projects, while the global role itself stays. Rows scoped to other workspaces, and memberships of the same person elsewhere, are untouched, with one exception: a membership in workspace B that holds a role owned by workspace A is invalid by the model (a role is only assignable inside its own workspace), and it is deleted when A is deleted, because the role it references goes away. **Account erasure and other people's access (owner decision 2026-10-15, #734):** a workspace is erased with the account only when nobody else can reach it. The check is built from the same predicates as `deleteWorkspaceRoleDependents` (`workspaceDependentPredicates`), so what deletion would remove is what erasure protects: besides the legacy `workspace_member` rows, any `membership`, and any non-revoked `membership_grant` (direct, JIT, OIDC or SCIM, including one that only derives from one of the workspace's group mappings), that targets the workspace, one of its projects or a role the workspace owns and belongs to another person, and any active, signed-in customer person of an organisation that one of the workspace's projects is bound to (they would lose those projects). If there is one, erasure stops with `409` ("Other people still have access to …") before anything is deleted; the workspace must be transferred or removed first. The tables `person`, `membership_grant` and `membership` — in that order, the provisioning writers' own order, so the lock cannot deadlock against them — are locked against writes (`SHARE ROW EXCLUSIVE`) from the check until the transaction ends, so no access can be granted in between. The other-access check runs first without the lock, so a refused erasure never takes it (a refused call cannot be repeated to stall writers); only a passing erasure locks, and then re-runs the same check under the lock. The lock wait is bounded by a 3-second `lock_timeout`; on timeout (SQLSTATE `55P03`) nothing has been deleted and erasure answers `409` ("…busy updating access. Nothing was deleted; try again…"). Rows of another scope that merely share the workspace id do not count. No migration; reversal path: switch those FKs to `ON DELETE CASCADE` in a forward migration and remove the helper. **Owner/admin reach carrier rows:** each workspace gets, on demand, at most one `role` row with `scope = 'workspace'`, `workspace_id` = that workspace and `key` `owner` and one with `key` `admin` (`is_system = true`, `is_editable = false`, ranks 100 and 80, `capabilities = []`). They exist only so the explicit owner/admin `sees_all` grant (below, decision log 2026-10-14) has a role to point at; authority for these roles is NOT read from them (the compiled-in built-ins via the legacy `workspace_member.role` remain the source), so they must stay empty and an IdP mapping can never target them (`admin`/`owner` keys are refused). A same-keyed custom (non-system) row is never trusted as the carrier **Project-lead role (decision log 2026-10-14, #435):** each workspace gets one `role` row with `scope = 'project'`, `workspace_id` = that workspace, `key = 'project-lead'`, `is_system = true`, `is_editable = true`, rank 50 and `capabilities` equal to the built-in `lead` list in [permissions](permissions.md) (a snapshot taken when the row is written; unlike the owner/admin carriers above it carries REAL capabilities). It is seeded for existing workspaces by migration 0124, for new workspaces by `createWorkspace`, and on demand by `ensureProjectLeadRole`; a same-keyed row that is not `is_system` is never trusted (no grant is made). It is granted to a project's creator through a direct `membership_grant` with `direct_origin = 'project_creator'`. An identity-provider mapping can never target it: the shared mapping validator accepts only workspace- and organisation-scope roles. |
| `team` | `workspace_id`, `name`, `capacity_days_per_week`, `is_cab` (exactly this team's members may decide CAB approvals). Unique `(workspace_id, id)` (`team_workspace_id_id_unique`, 0119) is the parent key for tenant-composite FKs |

## Authentication-owned tables

Better Auth owns `user`, `session`, `account`, `verification`, `two_factor`, `passkey`, and `apikey`. Their route/credential semantics remain bounded by TaskDesk policies; a library-owned table does not grant authority.
