# Second-wave audit — 8 Nov 2026

Eight read-only lenses beyond the first audit and the OpenAI and Gemini reports. A second reviewer tried to refute each high and medium finding. All findings come from reading code; nothing was run against UAT. Findings feed roadmap rows C8-7 onward.

## User journeys

Read-only walk of the five journeys in code, checked against features.md and screens.md. I found 9 new problems that are not in D1-D18, G1-G9, the R/F/W/S/TA/DOC ids, A8-*, C8-* or L-*. The biggest gaps are in onboarding (journey 4): an organisation can be missing from Customer invitations with no explanation; invitations reach a dead end when no email provider is set up; and a project's customer link is fixed at creation even when no organisation exists yet. In triage (journey 2), the work item made from a request is shown as plain text, and as a raw id after a reload. In journey 3, a queued report export can only be found again through an email link. In journey 1, customers approve without seeing what they are approving. First-run setup (journey 5) gives no next steps. No browser check was done, so every finding comes from reading the code.

## Accessibility

Read-only WCAG 2.2 AA pass over apps/web/src and packages/ui. The base is solid: Button has a focus-visible ring and a coarse-pointer 44px hit area, toasts and around 140 files use live regions, there is a reduced-motion stylesheet, skip links, and keyboard sensors on the board, list and calendar. The gaps are in particular components: icon-only buttons that have only a tooltip as their name, priority shown by icon alone, project reordering that works only by mouse or touch, global single-letter shortcuts that cannot be turned off, no focus move or announcement when the route changes, search results that are never announced, error toasts that disappear quickly, placeholder-only labels in the create dialogs, an invisible focus stop on tab panels, and auth pages with no main landmark. Excluded as already known: D6 (keyboard row link on the projects table) and D17 (missing h1 in general). Not in my lens, but worth a check: components/backlog-list-view/index.tsx and components/list-view/index.tsx are imported from nowhere outside their own folders and look like dead code (their siblings task-row and list-column-section are still used).

## Localisation

i18n lens, read-only. The biggest gap is that translation fallback cannot be seen. In every one of the 18 non-English locale files, about 5,800 to 6,000 of the 8,133 en-US strings are byte-identical English. This includes ja-JP and zh-CN, where English text can only mean the string was never translated. `pnpm check:i18n` compares key presence only, and `--fix` writes the English value into the locale, so i18next fallback never fires and CI prints OK. The language picker still offers all 19 locales. Server-generated text is English-only: notification titles, digest emails and API refusal messages. Email localisation is split across three resolvers that cover 4, 4 and 6 locales. The portal ignores the saved locale, and the three surfaces (portal, email chrome, terminology) read different locale sources. Smaller items: a custom-field formatter that is duplicated and not localised, a sentence built from fragments, and size and hours formatters that bypass the app locale. Nothing to report for RTL, because no RTL locale is supported. Missing keys in ja, ko, vi, zh and id are correct CLDR plural behaviour, not a defect. Everything here comes from reading files; nothing was checked in a browser.

## API quality

I did a read-only API-quality pass over apps/api/src, sampling about 40 routes across these modules: label, comment, activity, time-entry, time-tracking, task, v2/task, project, intake/portal, report, workspace, idempotency, auth and openapi. I checked the findings against the 8 Nov verification report, the roadmap rows A8-*, C8-* and L-*, and the Claude audit IDs. All 10 findings below are new, and IDs use the AQ- prefix so they don't clash with the existing API-1 to API-3.

What is in good shape:
- **Policy registry:** complete. tests/permissions/inherited-uncovered.json has 0 uncovered routes.
- **Idempotency:** the middleware runs on every unsafe request.
- **Pagination:** the canonical work-item and portal lists use cursors.

Main themes:
1. **Unhandled errors are not logged.** When a request fails with an unexpected error, the 500 is recorded with no cause.
2. **The old Kaneo routes still run on a separate `task` table.** These are the legacy task, comment, activity and time-entry routes. The canonical app never reads that table, and the only web screens that call these routes are no longer shown anywhere. The time-entry routes are the clearest data problem: time logged through them never reaches timesheets, costs or budgets.
3. **GET /api/project/{id} loads every task row** in the project.
4. **Errors come back in several shapes,** and the OpenAPI document does not match what handlers actually return.
5. **Session and portal users have no write throttle,** and the web app does not send idempotency keys.

No high-severity defect was proven. I ran no tests, containers or browser checks; every claim comes from reading the source at the cited lines.

## Test strategy

Test-strategy audit (read-only). The API side is strong: 472 integration files, 26 of them with real sign-in, real WebSocket reach tests, and a role x route matrix in tests/permissions. The browser side gives much less go-live confidence than its size suggests.

1. The only real-runtime browser security journeys gate nothing. tests/e2e holds 13 specs, among them self-approval, customer CAB, approver email leak and session cache. No CI job, test-all gate or testing.md entry runs them.
2. The 65 apps/web/e2e "journeys" mostly run against untyped page.route fixtures. 19 files hand-write capability objects, and the main journey spec grants every capability. RBAC and response-shape drift are therefore invisible in the browser.
3. The five e2e-sit specs only run on one machine. They read sign-in state and passwords from a dated, agent-specific macOS folder that no repo script creates, and they write evidence into tracked docs. The SIT smoke script uses a second credentials convention and checks only that access is allowed, never that it is denied.
4. Smaller items: phantom Playwright gates; fixed sleeps used to prove that something did not happen; G8 visual baselines that are all light-mode, desktop, happy-path; and a narrow cleanup gap in the org delete/restore SIT spec.

Proposed minimal persisted Playwright set, as concrete content for L-03a, run on local SIT under one shared config with global per-role sign-in. Each journey creates its own run-prefixed records with no reseeding, and each ends with an axe scan plus a 390 px dark screenshot.

J2 Customer B cannot open customer A's request, checked in the UI and on the direct API URL.
J3 An agent session is refused on the portal host and a customer session is refused on the agent host.
J4 Lead edits a project and board columns; member and viewer get "no access" on the same direct URLs.
J5 Member moves a card on the board, comments and attaches a file; everything persists after reload.
J6 Viewer sees work read-only, with no write controls rendered.
J7 Approvals requester to approver on SIT, plus the self-approval denial.
J8 KB article published by an agent is readable on the portal.
J9 Realtime with two contexts: an inbox update appears without reload.
J10 Admin God Mode organisation lifecycle (the existing spec, made disposable).
Promote J2, J3, J4 and J6 into the post-deploy smoke subset.
