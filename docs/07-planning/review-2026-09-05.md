# Planning review — 2026-09-05

A full read of the corpus before P0 starts, answering three questions Thomas asked:
**is the documentation complete enough to build from, is each phase enough to ship and
sell, and what should change to make v2 a better product.** Findings are recorded here;
the fixes they produced are in the [decision log](decision-log.md) and applied in place.

## Method

1. A deterministic pass — every relative link and heading anchor in 104 markdown files (as the corpus stood at that
   pass; 126 after the same-day closure additions, ~136 after 2026-09-06)
   checked by script (zero broken links, zero missing anchors; the one flagged link is the
   ADR template placeholder).
2. A direct read of the hub documents and every file touched in the previous session, plus
   targeted searches of the corpus for features the reference systems have.
3. A parallel review by thirteen independent reviewers on the strongest model tier —
   one per documentation section, plus a cross-document consistency check, a per-phase
   shippability/sellability assessment, and a separate **security review**, per the
   [model-tier policy](../04-engineering/agent-workflow.md#model-tiers-within-claude-code).
4. Feature mining from the reference systems (kaneo, Plane, OpenProject, TaskDesk v1, the
   six ITSM clones), each candidate then verified against the corpus and classified as
   present, partial or missing. Findings from 3 and 4 are in the
   [parallel audit](#findings-from-the-parallel-audit) section below.

## Verdict

**Before the parallel audit:** it looked ready for P0 with fixes. **After it: not
buildable as written — and now substantially closer.** Four independent reviewers (all
Opus; the security review completed after the others and its findings were folded in the
same day) converged on
one diagnosis: the reasoning is strong, but the prose outran the schema, the capability
vocabulary and the screen register. Concretely, before the closure pass, an implementer
would have had to invent eight tables, ~25 columns, a policy syntax the registry could not
express, a state-scoping rule that made the lifecycle engine unbuildable, a colour palette,
and the built-in roles' capabilities. Those are now fixed in the documents themselves — see
[Findings from the parallel audit](#findings-from-the-parallel-audit). What remains (~300
medium/low, per-spec) is tracked in [reviews/2026-09-05/](reviews/2026-09-05/) and closed
at each feature's SDLC stage 2, recorded as **P0 step 0** in [phases.md](phases.md).

**P0 can start.** Its own task list is concrete, and the closure pass gave it the week-one
documents it lacked. The two decisions this review left open for Thomas were **both closed
the same day** in his confirmed decision document: per-request visibility inside a
customer organisation is `private` / `organisation`, default `organisation`, request types
may force `private` ([customer-portal.md](../03-features/customer-portal.md) `CP-16`); and
the per-feature verdicts in the [inherited-features register](../01-architecture/inherited-features.md)
are final — every inherited integration router and `public-project` are removed at fork
([decision-log.md](decision-log.md)).

## Is each phase enough to ship and sell?

Honest answer: **no, not each one — and the plan is better for admitting it.** The
detailed mapping is in [release-plan.md](release-plan.md). In one table:

| Phase | Shippable | Sellable | To whom |
| --- | :-: | :-: | --- |
| P0 Foundation | — | — | Infrastructure. Its value is that P1–P4 can be built without design debt |
| P1 Core work | ✅ internal | ❌ | kaneo is free; parity with it is not a product. Replaces Planner internally |
| P2 Service desk | ✅ pilot | 🟡 pilot | An internal IT/support team |
| P3 Portal + identity | ✅ pilot | 🟡 pilot | An MSP or agency with customers |
| **P4 Governance** | ✅ | **✅ `2.0.0`** | **First real sale: self-hosted customers who configure it themselves** |
| P5 Insight + agile | ✅ | ✅ `2.1` | Delivery teams; leadership |
| P6 Import | ✅ | ✅ `2.2` | Anyone migrating off another tool |
| P7 Polish | ✅ | ✅ `2.3` | **External paying customers, marketplace** — gated by the penetration test, not by features |

The regrouping that follows from this — pre-release channels through P3, `2.0.0` at P4,
minors after — is the [release plan](release-plan.md). Selling before P4 is selling a
pilot and should be priced and promised as one.

## Recommendations

Ordered by when they bite. Each one that is adopted becomes a decision-log entry; each
one that is rejected should too, so the next reviewer does not raise it again.

### Before P0 step 1 — the kaneo inherited-features register

P0 says "copy kaneo, de-brand, strip billing and cloud-only pieces." That names what to
*remove*; it does not name what is being *kept*, and kaneo carries features the v2 specs
never mention — visible from its dependencies alone: a **GitHub integration** (`octokit`,
`@octokit/webhooks`), a **Planka importer** (`packages/planka-import`), Markdown
import/export and Mermaid diagrams in rich text (`turndown`, `react-markdown`, `mermaid`,
`shiki`), a second schema library (`valibot`) alongside Zod, and a second client-state
library (`nanostores`) alongside Zustand. Every one of these is either a feature we ship
without a spec, or dead code we carry without a decision.

A listing of kaneo's actual feature folders (`apps/api/src`, `apps/web/src/components`,
`packages`) makes the point concrete. kaneo today ships — and v2 therefore inherits on
day one of P0 — all of the following:

| kaneo feature | v2 spec today | Register verdict to make |
| --- | --- | --- |
| `github-integration`, `gitea-integration` | none | ~~Keep, write a spec~~ → **Remove at fork** (decided 2026-09-05). `external_link` and the reserved `devlink` kind are the extension point; future order GitHub → GitLab → Gitea → Bitbucket → Azure DevOps ([roadmap.md](roadmap.md)) |
| `slack-integration`, `discord-integration`, `telegram-integration`, `generic-webhook-integration` | notify plugins cover Slack, Discord, webhook | ~~Keep; fold into notify~~ → **Remove at fork** (decided 2026-09-05). They return, if at all, as `notify.*` plugins in the order Teams → Slack → Telegram → Viber; our signed webhooks are written fresh in P4 |
| `workflow-rule` (automation rules) | [automations.md](../03-features/automations.md), P4 | Keep — the accelerated plan lists automations as *built* in P4, but a working engine is inherited in week 1 |
| `time-entry` | [time-and-cost.md](../03-features/time-and-cost.md), P5 | Keep — basic time entries are inherited, not deferred; rates and budgets remain P5 |
| `public-project` (public, anonymous project boards) | none — listed only as a Plane-inspired candidate below | ~~Decide~~ → **Remove at fork** (decided 2026-09-05, section C): routes, handlers, screens and any dormant code deleted; `feature.public_boards` reserved with no implementation |
| `gantt`, `calendar`, `backlog-list-view`, `kanban-board`, `list-view`, `bulk-selection` | [views.md](../03-features/views.md) — calendar/timeline are P5 | Keep — **calendar and gantt are inherited, not built later.** The accelerated plan's deferral register is wrong about them |
| `command-palette`, `keyboard-shortcuts-help`, `search`, `onboarding`, `profile-setup`, `team` | covered | Keep |
| `scheduler`, `mcp`, `oauth`, `invitation`, `notification-preferences`, `external-link`, `task-relation`, `column`, `activity`, `storage`, `plugins`, `instance` | covered | Keep — these are the mechanisms the v2 specs already assume |
| `billing`, `trial-card`, `demo-alert` | rejected in [competitive-inspiration.md](../00-overview/competitive-inspiration.md) | **Remove** |
| `packages/planka-import` | not in import scope | **Remove** (or park as an `import.planka` plugin if trivially cheap) |
| `valibot` alongside Zod; `nanostores` alongside Zustand | tech-stack says Zod, Zustand | **Remove**; consolidate |
| Markdown import/export, Mermaid, code highlighting (`turndown`, `react-markdown`, `mermaid`, `shiki`) | rich text mentions Tiptap only | Keep; add to [comments-and-activity.md](../03-features/comments-and-activity.md)'s rich-text section |

**Recommendation:** make P0 step 1 produce this table as a one-page **inherited-features
register** in `docs/01-architecture/`, completed with the kaneo commit SHA taken, and
treat any inherited feature with no v2 spec as **feature-flagged off** until its spec
exists and it has passed the UX gates — inherited code is still code that can leak data
(the public boards especially) or contradict a decision (billing).

Two consequences for [accelerated-delivery-plan.md](accelerated-delivery-plan.md), now
noted there: calendar/timeline views, basic time entries and the automation engine are
*inherited in week 1*, not deferred to the 3-month window — the deferral register
overstated what is missing; and `public-project` is **deleted in P0 step 1** (decided
2026-09-05), so no unauthenticated read surface reaches the router retrofit at all.

### Process

- **Phase reviews should include a "features inherited or dropped" line.** The kaneo
  register above is the first instance of a recurring question: every time a reference
  system is mined, what was consciously *not* taken should be written down too.
- **Threat model as a document.** The [security model](../01-architecture/security-model.md)
  is strong on controls and thin on adversaries. A one-page threat model — malicious
  workspace admin, hostile customer organisation, compromised plugin credential, insider
  with database access, compromised upstream (kaneo) — gives the Opus security reviews a
  fixed list to check against instead of re-deriving it each time. See the security
  findings below.
