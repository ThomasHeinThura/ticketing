## Security findings reviewed

- **Authorization and scope:** Current creation admits one live `work_item` deletion and derives its non-null workspace after repeating access/capability checks and locking target/parent rows. Expiry only changes an already-persisted pending decision; it does not execute or delete the target. The worker filters `workspace_id IS NOT NULL` before its ordered candidate cap and separately detects due null-scope rows as degraded operation without changing them. Canonical storage permits nullable workspace, but current event/outbox requires workspace; future organization/instance event support is tracked by [#564](https://github.com/ThomasHeinThura/ticketing/issues/564). This review does not claim those future scopes are supported.
- **Clock and terminal state:** Due selection uses PostgreSQL `clock_timestamp()` and `(expires_at,id)` ordering with `FOR UPDATE SKIP LOCKED`. While holding each row lock, the worker samples the database clock again and conditionally updates only `state='pending' AND expires_at <= decided_at`; both fields are `timestamptz`. Terminal actions remain unchanged, and a row that becomes due after selection waits for a later run.
- **State/event atomicity:** The conditional state transition and registered `pending_action.decided` outbox record share one transaction. The system actor, key, URL, action id, `expired` outcome, and decision timestamp are used without secret details. Outbox failure rolls back the state. Row locking plus the conditional update makes repeat runs and overlapping lease owners idempotent for each action.
- **Audit exception:** Audit append runs in a nested savepoint on the same session. A caught audit failure rolls back that savepoint, is logged and reported as degraded, while the state/event transaction may commit per PA-11/AU-14. Durable AU-14 counter/alert and administrator notification remain unfinished program work.
- **Progress and races:** Keyset batches limit selected/processed eligible rows to 1,000 per invocation; this is not a physical tuple-visit cap. A SQL eligibility filter prevents a large unsupported null-scope prefix from consuming that candidate limit, with a regression for 1,001 such rows followed by eligible work. `SKIP LOCKED` allows a new lease owner to work on unlocked rows while an expired owner finishes; terminal-state conditions, rather than the lease, provide idempotency. Database-controlled cancel-first and worker-first cases assert one terminal outcome/event/audit, and the overlap regression checks one event per row.
