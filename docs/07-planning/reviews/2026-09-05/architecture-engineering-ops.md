## 1. `docs/01-architecture/` — core architecture documents

**Verdict: strong intent, not yet buildable.** The reasoning is unusually good — the
reach/authority split, the policy registry, lazy SLA, the outbox, the two-origin analysis
are all better than most greenfield designs get. But the corpus does not yet hang together
as a specification: three documents name six database tables the data model does not
define; the job table in `overview.md` disagrees with `background-jobs.md` on names and
count; the "typed client" is described two mutually exclusive ways; and the two hardest
mechanisms in the system (runtime better-auth rebuild, cross-replica `job_lease`) are
described in prose that an implementer would have to invent the real design behind — and
the one code snippet given for leasing is wrong as written. A P0 implementer starting from
these documents would make consequential guesses in week one.

## 5. `docs/06-data-import/` — import strategy, field mapping, Azure DevOps, Plane

**Verdict: the most complete and realistic document group in the corpus, with one
architectural collision nobody has noticed.** The two-path model (structured plugin +
agent-assisted through MCP), the insistence that unmapped values *block* rather than guess,
the `completed`/`cancelled` distinction, the explicit "not imported" lists, the "Plane guest
≠ our viewer — check this" warning and the placeholder-person rule are all the marks of
someone who has actually done a migration. The collision is that a multi-hour import running
as an in-process job on the request event loop, through the normal mutation path, will
generate hundreds of thousands of activity rows, outbox rows and WebSocket broadcasts — and
no document says otherwise.

## Summary

**The corpus is above average for a greenfield project and below the bar for handing to an
implementer on Monday.** The thinking is genuinely good — the reach/authority split, the
route-policy registry with CI enforcement, lazy SLA evaluation with an explicit cache
contract, the outbox, the honest ADR "Negative" sections, the two-origin analysis that
correctly refuses to treat a bundle as a security boundary, and an SDLC whose stage 2 is
design rather than paperwork. Several documents (`error-fix-loop.md`,
`definition-of-done.md`, the import group, `release-plan.md`'s channel model) are ready to
use as-is.

What holds it back is that it has been written as a persuasive whole rather than as a
specification, and three specific classes of defect follow from that:

1. **Identifier lists are duplicated instead of referenced, and they have already
   diverged.** Job names, feature flags, bootstrap environment variables, capabilities and
   route paths each appear in two or three documents with different contents. Six tables
   (`work_item_sla_cache`, `metric_snapshot`, `workspace_feature_flag`, `idempotency_key`,
   plus missing columns on `attachment`, `organisation`, `audit_log`, `session`, `person`)
   are named by documents that depend on them and absent from the data model. Fixing this is
   mostly clerical and should happen before P0, because these lists are the inputs to the CI
   gates the whole quality argument rests on.

2. **The three hardest mechanisms are described in prose, not design.** Runtime better-auth
   reconstruction, cross-replica `job_lease` (whose one code snippet is wrong in three
   ways), and the terminology overlay meeting i18n are each a week of work with real failure
   modes, and each is currently one paragraph. Add the boot-time migration advisory lock,
   the per-portal cookie strategy, and encryption-key rotation — described as a God Mode
   button on a value that lives in `.env` — and that is six places where an implementer must
   guess, in the areas where guessing is most expensive.

3. **Several promises exceed what the described stack can deliver, and the calendar exceeds
   what the described process can absorb.** Plain Compose cannot do the zero-downtime
   upgrade; the jobs-replica escape hatch needs the code change it says it does not; there
   is no OpenAPI 3.2 validator; a 15-minute PR pipeline cannot contain Testcontainers plus
   four Playwright projects; CI both "never deploys" and deploys UAT automatically; the
   installer's checksum does not defend against the threat it is presented as addressing;
   the AWS anti-tamper requirement is structurally unsatisfiable in an AGPL self-hosted
   product; and six full phase gates — each requiring VoiceOver **and** NVDA passes, a
   fresh-eyes test, four browsers, a load baseline and an Opus security review — cannot fit
   in five weeks with one human. The right response is not to weaken the gates; it is to
   publish the reduced scope and the deferral register in `release-plan.md` so the trade is
   visible rather than discovered at the first missed gate.

**On kaneo specifically**, the claims are optimistic in a way that hides P0 work. kaneo has
no `packages/ui`, no `packages/domain`, no `packages/plugins-contracts`, no
`packages/importers` and no `packages/i18n`; it has 18 locales, not 22; its primitives are a
**mixed Radix + Base UI** set inside `apps/web`, so "accessibility comes from Radix, once"
is untrue on day one; it ships neither Storybook, Playwright, axe, TanStack Table, Recharts,
dependency-cruiser, Pino nor prom-client, all of which the quality gates require; five of
the seven agent skills said to be "taken from kaneo" do not exist there; and the `job_lease`
table that two ADRs treat as inherited could not be confirmed (`croner` genuinely is a
dependency). ADR 0008 is the one document that tells the truth about the extraction cost —
ADR 0001, `tech-stack.md` and `monorepo-layout.md` should be corrected to match it.

**Recommended sequence before P0 starts:** (1) one editing pass that makes the data model
authoritative for every table and column, and every identifier list single-homed; (2) the
four week-one missing documents — repository bootstrap, `packages/ui` extraction, migration
convention, Dockerfile spec — plus the CI platform decision; (3) design notes for the three
hard mechanisms; (4) an honest scope-and-deferral pass on `release-plan.md`. That is a few
days of writing that removes essentially every high-severity finding above, and it is far
cheaper now than as rework in week three.
