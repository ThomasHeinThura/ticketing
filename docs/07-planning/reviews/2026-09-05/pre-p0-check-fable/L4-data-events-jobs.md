Sweeping backticked and unbackticked route-table forms across all specs produced no capability outside the registry - the only near-misses are documentation placeholders (`resource:action`, `project:xyz`, `instance:manage_*`, `mcp:*`) and non-capability colon strings (`check:deps`, `taskdesk:control`, `label:urgent`, `state:started`). **The capability registry is clean.**
- **Feature flags:** 22 `feature.*` keys in plugin-architecture.md:243-261; every flag used anywhere is registered, and every registered flag is used. **Clean.**
- **`state` vs `status` (rule 11):** three violations survive - approvals.md:35 (`approval.status`), storage-and-attachments.md:52 and :60 (`status = pending` / `= ready`). Everything else matching `status` is HTTP (`status_code`, `response_status`) or a docs-progress column.
- **Tenancy (rule 5):** of the 111 tables, the ones holding tenant data with **no** scoping column and no single-hop parent are `attachment` (needed by its own object-key template), `custom_field_value`, `external_link`, `outbox`, `import_run`/`import_record_link`/`import_mapping_profile`, and `metric_snapshot` (jsonb only). Everything else reaches `organisation_id`/`workspace_id`/`project_id` in one hop.
- **Job lease (rule 7):** the acquire/heartbeat/release SQL at background-jobs.md:28-43 **is correct Postgres** - `ON CONFLICT … DO UPDATE … WHERE job_lease.expires_at < now()` returns a row only when the update fires, the heartbeat's owner predicate is right, and release is owner-scoped so a lost lease cannot be released out from under its new holder. It is also **already implemented upstream**: kaneo `apps/api/src/scheduler/leader-lock.ts:19-42` ships the identical statements (without the heartbeat), against `job_lease` at `apps/api/src/database/schema.ts:480`.

## Top 5

1. **`schedule_transition` has no storage** (data-model.md:206 vs workflows.md:101, background-jobs.md:67) - the "pending until" effect is in the closed vocabulary, `reminder-scan` claims to fire it, and no table or column records the pending transition, its due time, or the from-state that cancels it.
2. **The audit hash chain is not buildable as written** (data-model.md:293, audit-trail.md:93) - "canonicalised row" is never defined, no writer serialisation is stated for multiple replicas, `organisation_id ON DELETE SET NULL` mutates a hashed column, and `audit-purge` truncates the chain's head with no anchor.
3. **`first_response` SLA cannot be computed** (sla.md:76 vs data-model.md:157, ADR 0009:27-33) - half of `sla_goal.metric` has no stored fact behind it; and `sla-scan`'s candidate SQL excludes `resolved_at is not null`, so `sla.met` can never fire from the job that background-jobs.md:66 says emits it.
4. **Mechanisms with no columns**: `workflow_transition.is_reopen` (`WF-21`, `CP-8`), the per-organisation legal-hold flag that three jobs must honour, the six per-organisation quotas that return 429, and `comment` tombstones (`CA-18`).
5. **Two authoritative documents disagree about kaneo** (background-jobs.md:11 "the `job_lease` table is ours to write" vs ADR 0007:17 "kaneo already ships … a `job_lease` table") - and the ADR is right: kaneo HEAD ships the table *and* the acquire SQL. What is genuinely ours is only the heartbeat and the abort signal.
