# Testing the whole product

Testing is whole-product, not per phase (Thomas, 28 Oct 2026). Three levels; each change goes through code → feature → design → browser testing ([AGENTS.md](../AGENTS.md)).

## Level 1 — every pull request

GitHub CI is a required gate. All required checks must pass; a failing gate is fixed, never exempted or retried until lucky.

| Area | CI job / local command |
| --- | --- |
| Code | `pnpm lint:ci`, `pnpm typecheck`, `pnpm test` (unit + component, 3 CI shards), integration on PostgreSQL 18 (8 shards, `vitest.integration.config.ts`), `pnpm test:permissions`, `pnpm check:route-policy`, domain coverage 90% |
| Contracts and registers | `pnpm test:contract` (OpenAPI drift; breaking changes need Thomas's approval in `scripts/ci/openapi-approved-breaks.json`), env/vocabulary/events/reviews/skips/overrides registers, gate checkers + red probes, CI matches `ci-gates.md` |
| Features | `pnpm test:e2e` (mock-backed and Testcontainers journeys, `apps/web/e2e/`; 8 CI shards: 4 over everything except `*-persisted.spec.ts`, 4 over those) |
| Design | `pnpm check:ui:raw-elements` (raw controls, library `Input` date/time/checkbox/radio types, native `title` tooltips on interactive hosts), `pnpm check:tokens` (contrast), visual regression G8 (`pnpm test:visual` in the pinned `mcr.microsoft.com/playwright:v1.63.0-noble` container; regenerate baselines only for intended changes and keep the committed PNG of every screen you did not change: a local refresh of `project-module-detail` and `project-prerequisites` shifted 46 and 13 pixels by one colour level, the board gradient sits on a rounding step, and CI rejected it), accessibility G4 (axe) |
| Performance | G11 and G13 both run in the single `performance - budgets (G11)` job (`pnpm test:perf`). That job is not a required check on `main` (removed 5 Nov), so neither blocks a merge; read them as report-only and diagnose misses in the app. Bundle budgets are enforced by `pnpm check:bundle-size` in required fast CI. Thresholds never change without Thomas |
| Security | Gitleaks secret scan, dependency audit, CodeQL, Trivy (release image) |

Locally before opening the PR: run the affected targeted tests first, then the gates above that the change touches, then open every affected screen on local SIT (below). Integration tests use a fresh dedicated `_test` database — never the live `taskdesk_browser_journey_1022_test` (62870).

If calibration stops the performance job before G13 runs, G13 remains unmeasured. Qualify it with the unchanged test cases and budgets; report-only G11 status does not establish a G13 pass.

## Level 2 — every release (merge to `main`), before deploying

1. **Release smoke** — `pnpm sit:smoke` (read-only; signs in every account in `~/.taskdesk/sit-credentials.json`, checks the API and opens the main agent and portal screens in Chromium, failing on HTTP 5xx/429, page or console errors and error boundaries). Against Technexus: `NODE_EXTRA_CA_CERTS= pnpm sit:smoke -- --agent https://<agent host> --portal https://<portal host> --credentials <file>`.
2. **Release regression suite on local SIT** (backlog L-03a, first slice): `SIT_ACCOUNTS_FILE=<private JSON array of {role, host, email, password, totpUri?}> pnpm test:release` runs, in order and stopping at the first failure, the release smoke (waits up to 120 s for both hosts), the persisted journeys `apps/web/e2e-sit/release-*.config.ts` against `https://ticketing.localhost` / `https://portal.localhost`, and `pnpm test:permissions`. `RELEASE_SWEEP=1` appends the screen sweep (long; it writes to SIT). Origins default to local SIT (`SIT_AGENT_ORIGIN`, `SIT_PORTAL_ORIGIN`); Node trusts `deploy/local/certs/local.crt` unless `NODE_EXTRA_CA_CERTS` names the certificate your proxy actually serves (a fresh worktree has no `deploy/local/certs`); Chromium skips the certificate check for `*.localhost` only. Journeys discover the workspace and project through the API as the signed-in user (pin them with `SIT_RELEASE_WORKSPACE` / `SIT_RELEASE_PROJECT`, a name, slug, key or id), create and remove their own work items, cycles and the like, never touch existing records and never run the seeder. Optional accounts-file roles `customer-other` (customer of another organisation, host `portal`) and `instance-admin` switch on the organisation-isolation check and the `release-import-apply` journey (an instance administrator always has TOTP after setup, so its entry needs the `otpauth://` `totpUri` from enrollment; sign-in answers the two-factor challenge with it, and it must be a member of the release workspace and of the release project with a role that creates work items, because imports also check workspace read and `work_item:create` there); without an `instance-admin` the suite lists that journey as NOT RUN (never as passed). The reports-kb journey needs the knowledge base on for the release workspace and fails otherwise. The whole run is bounded to 60 minutes, and `RELEASE_SWEEP=1` runs axe through `@axe-core/playwright` (only `critical` violations count as issues; the rest are warnings). Each step runs in its own process group, killed whole on timeout. The reports-kb journey reuses one article titled "release-suite probe article" (published for the check, archived after); the service-desk journey leaves one accepted submission per run as known residue. The release-feature-off and release-planning journeys change a project feature override and restore it in `finally`. Older seed specs in `apps/web/e2e-sit/` need private state files from the original SIT and are not part of the command.

## Setup

Use the pinned pnpm and Node 24+. Local SIT: one deployment using only `deploy/compose.testing.yml`. After independently verifying the initial restored database/files, set absolute private `SIT_COMPOSE_ENV` and `SIT_PRIVATE_DIR` paths and run `scripts/deploy.sh local`; its private Compose inputs must pin `SIT_IMAGE` to a signed release digest and set `TASKDESK_IMAGE_TAG` to the matching signed tag. It verifies both provenance and the cosign signature before pulling, runs the isolated migration and checks readiness without seeding or generating secrets. Images are built with `VITE_API_URL=''`. Never rerun the SIT account seeder against an existing database or reset customer data. Integration databases: scratch PostgreSQL 62871 or Testcontainers, one new `_test` database per run, dropped afterwards. Generators (`openapi:write`, matrix regen, `generate:route-metadata`, web builds) run one at a time; `pnpm check:tokens` rebuilds `dist`, so never run it during a bench.

**Standalone backups:** use `scripts/backup-maintenance.sh --project-name <name> --backup <new-id>` in a planned maintenance window; `scripts/backup.sh` only verifies the held barrier and refuses otherwise ([operations runbook](technical/operations-and-distribution.md#backup-and-restore-method)). Its offline tests are `scripts/ci/backup-maintenance.test.mjs` and `scripts/ci/backup-dump-list.test.mjs`. Real backup and restore qualification requires the operator run on local SIT (Phase 2); the offline tests do not establish it. The local SIT reset keeps its own `local-fresh` gate below. Never point either at native PostgreSQL 62870.

For the owner-approved local SIT reset, set canonical private `SIT_COMPOSE_ENV` and `SIT_PRIVATE_DIR` outside the checkout and selected volumes, and close all three registration/workspace switches (`true`). Run `scripts/deploy.sh local-fresh` first (preview is the default; `--dry-run` is equivalent, and `--dry-run-allow-open-registration` requires explicit `--dry-run`) to inspect the observed Docker daemon ID, active context/socket endpoint, `taskdesk-codex-testing` project, and exact container IDs and volume names with no changes. Then run `scripts/deploy.sh local-fresh --confirm-wipe taskdesk-codex-testing --confirm-daemon <daemon-id>` with that previewed daemon ID: the one-shot command verifies the daemon identity before locking, stopping, disconnecting or removing anything, stops the application, isolates the database, and requires a same-run backup and scratch restore proof before removing re-verified project resources. Interrupted runs require the daemon-verified manual inspection and recovery procedure in [operations and distribution](technical/operations-and-distribution.md); private backups contain plaintext secrets and native PostgreSQL 62870 is excluded.

The manually dispatched PR-candidate workflow uses a separate package, signature identity and attestation from `release.yml`. It binds an exact same-repository feature SHA to the trusted main workflow SHA, scans both image platforms before publication, and marks the output for local SIT only. A candidate image is never a production release. The workflow does not deploy or replace local SIT data; candidate selection and recovery require their own reviewed path and approval before the first run.

Screen sweep (local SIT only): `node scripts/sit/screen-sweep.mjs --agent-origin https://ticketing.localhost --portal-origin https://portal.localhost --accounts <json> --out <new dir outside the repo> [--roles a,b] [--widths 1440,768,390] [--themes light,dark] [--routes <regex>] [--concurrency 3]`. `--accounts` is a private JSON array of `{role, host: "agent"|"portal", email, password}`; `--out` is created 0700 and must not exist. For every role it signs in through the UI, discovers reachable IDs through the app's API, visits each `docs/screens.md` route per width and theme, and writes `results.json`, `summary.md` (issue counts, failing routes, role × route denial matrix) and full-page screenshots under `shots/`. Axe runs only if `@axe-core/playwright` resolves from `apps/web`; only `critical` violations count as issues, `serious`, `moderate` and `minor` are listed as warnings by impact in `summary.md`. A visit can write (default dashboard creation, KB view counts) and screenshots show account data, so keep the output private and never run it against another environment.

## Honest evidence

Never report a test name, screenshot count or CI status as proof of a journey that did not run. Distinguish mocked from persisted evidence. Record unavailable tooling and external credentials as blockers. Keep performance thresholds; diagnose failures.

Report history is read-only in `docs/archive/reports/`; generators write current output to `docs/report/`, reading the archived data baseline when current data is absent.

Report maintenance: run `node --test scripts/report/build-data.test.mjs`, then `node scripts/report/build-data.mjs` and `node scripts/report/generate.mjs` from the repository root. The rebuild derives counts only from the per-ID requirement index, retains every maintained phase and its acceptance/review/evidence metadata, and preserves the report timestamp; update that timestamp explicitly when recording new evidence. Invalid input or contradictory locked counts fail before replacement. The optional historical audit-directory argument is accepted with a warning and ignored; it cannot promote verification. Review the data/HTML diff and open the report at desktop, tablet and mobile widths in both themes before committing.
